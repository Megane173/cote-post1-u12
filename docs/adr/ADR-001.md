# ADR-001: Capas simples para persistencia y conservación del punto de extensión de notificaciones

**Estado:** Aceptado  
**Fecha:** 2026-10-30

## 1. Contexto

Tras integrar los patrones Chain of Responsibility, Strategy y Observer en el sistema de solicitudes de reembolso, se debe decidir si `SolicitudReembolsoService` debe migrar a una arquitectura Hexagonal o mantener la arquitectura en capas simples.

Se tiene como criterio de implementación de la arquitectura Hexagonal que el sistema debe sobrevivir tres años o más con cambios de infraestructura. Para aplicar este criterio, se evalúan por separado la persistencia y las notificaciones.

- **Persistencia:** `SolicitudReembolsoService` depende directamente de `RepositorioSolicitudesJpa`. Actualmente no existe ningún plan para cambiar el motor de base de datos.
- **Notificaciones:** el servicio depende de la interfaz `ObservadorCambioEstado`, que permite desacoplarlo de los tres notificadores concretos. Contabilidad ha anunciado una integración con una API externa para el próximo trimestre.

La información disponible no establece expresamente que el sistema vaya a mantenerse durante tres años o más. Por tanto, no puede afirmarse que se cumpla íntegramente ese criterio temporal. Sin embargo, la persistencia no tiene un cambio de infraestructura previsto, mientras que las notificaciones sí tienen una integración externa anunciada. Estas diferencias fundamentan las decisiones siguientes.

## 2. Decisión

### 2.1. Persistencia: mantener las capas simples

`SolicitudReembolsoService` continuará dependiendo directamente de `RepositorioSolicitudesJpa`. No se introducirá, por ahora, un puerto de persistencia adicional ni un adaptador JPA separado.

La decisión se fundamenta en que no existe un plan para cambiar el motor de base de datos ni se ha identificado otra necesidad actual que justifique esa abstracción. Con los datos disponibles, no se demuestra que la persistencia vaya a experimentar cambios de infraestructura que justifiquen adoptar arquitectura Hexagonal por este motivo.

Introducir un puerto únicamente ante la posibilidad hipotética de sustituir la base de datos añadiría complejidad sin un beneficio inmediato identificado.

### 2.2. Notificaciones: conservar `ObservadorCambioEstado`

Se conservará la interfaz `ObservadorCambioEstado` sin introducir, por ahora, otro puerto de notificación ni modificar la dependencia de `SolicitudReembolsoService`.

El servicio ya comunica los cambios de estado mediante una interfaz, sin conocer los detalles de `NotificadorEmpleado`, `NotificadorContabilidad` y `NotificadorAuditoria`. Por ello, la integración anunciada podrá implementarse en `NotificadorContabilidad` sin modificar el servicio central, siempre que se mantenga el contrato actual de notificación.

El cambio de infraestructura sí está identificado y previsto para el próximo trimestre, aunque no se ha establecido la vida útil total del sistema necesaria para confirmar el umbral de tres años indicado en la guía. Se considera que el punto de extensión existente es suficiente para la decisión actual, sin anticipar abstracciones adicionales antes de conocer los requisitos concretos de la API.

La implementación futura deberá contemplar aspectos que la interfaz actual no garantiza, como los reintentos, la gestión de errores y la recuperación ante fallos del sistema externo.

## 3. Consecuencias

### Positivas

- Se evita introducir un puerto y un adaptador de persistencia sin una necesidad concreta que los justifique.
- Se conserva la separación existente entre `SolicitudReembolsoService` y las implementaciones concretas de los notificadores.
- La integración de Contabilidad podrá implementarse sin modificar el servicio central, siempre que se mantenga el contrato de `ObservadorCambioEstado`.
- Se limita la complejidad adicional a las necesidades identificadas, aprovechando el punto de extensión que ya existe para las notificaciones.

### Negativas

- `SolicitudReembolsoService` depende directamente de `RepositorioSolicitudesJpa`, una interfaz vinculada a Spring Data JPA. Aunque no depende de una implementación concreta, sí mantiene una dependencia del framework de persistencia.
- Si en el futuro se necesita sustituir el motor de base de datos o disponer de varias implementaciones de persistencia, podría ser necesario introducir un puerto y un adaptador, además de modificar el servicio para depender del nuevo contrato.
- La interfaz `ObservadorCambioEstado` no garantiza por sí sola la entrega fiable de las notificaciones ni resuelve los problemas de disponibilidad, latencia y reintentos de la futura integración externa.
- En la implementación actual, los observadores se ejecutan después de guardar el cambio de estado. Si una futura llamada síncrona a la API falla en ese punto, la solicitud podría quedar guardada aunque la operación devolviera un error al cliente. Este comportamiento deberá tenerse en cuenta al diseñar la integración de Contabilidad.
